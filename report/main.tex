\chapter*{\centering Abstract}
\addcontentsline{toc}{chapter}{Abstract}
\begin{spacing}{1.15}
\noindent
\textbf{StudyMate AI} is a cross-platform mobile application that acts as an AI-powered
study companion for university students. The project was developed over a period of
thirteen weeks (July 5, 2026 -- September 30, 2026) by a two-member team following an
iterative, Agile-inspired software development life cycle combined with structured project
management practices. The application is built with React Native using the Expo framework
and TypeScript on the client side, a Node.js/Express REST backend on the server side, and
the Google Gemini large language model for all AI capabilities. Firebase Authentication
provides secure email/password sign-in, sign-up, and password recovery, while local,
per-user persistence is realized through AsyncStorage. The main features of the system are:
an intelligent streaming AI chat assistant; automatic structured summarization of uploaded
lecture PDFs; on-demand generation of multiple-choice quizzes for any topic with
selectable difficulty; a personal notes manager with search and edit support; and a study
planner with progress tracking that is reflected on a personalized home dashboard.

This report documents the full software development and project management process:
feasibility analysis, functional and non-functional requirement engineering, work breakdown
structure, activity scheduling with a Gantt chart, critical-path (CPM) analysis, effort
estimation, risk management, system architecture and detailed design (use-case, component,
sequence, and data models), implementation, and testing. All diagrams were produced
directly in \LaTeX{}. The system passed 30 out of 30 designed test cases during system
testing, and the finished product satisfies all planned functional requirements within the
scheduled timeline.

\vspace{0.4cm}
\noindent\textbf{Keywords:} mobile application, React Native, Expo, artificial
intelligence, large language model, Firebase authentication, PDF summarization, quiz
generation, Agile development, project management, CPM.
\end{spacing}

\chapter{Introduction}

\section{Background of the Project}
University students juggle many courses, readings, and examinations within limited
time, while lecture content is scattered across PDF slides, textbooks, and notes.
At the same time, large language models (LLMs) have matured into practical tools that
can answer academic questions, condense long documents, and generate practice
questions on demand.

The \textbf{StudyMate AI} project combines these observations into one mobile
application: (i) a conversational AI assistant, (ii) automatic summarization of
lecture PDFs, (iii) automatic multiple-choice quiz generation, (iv) personal note
management, and (v) study planning with progress tracking. It targets Android and
iOS through a single React Native (Expo) codebase and integrates Google Gemini AI
through a lightweight Node.js backend.

\section{Problem Statement}
Existing study tools are fragmented: students use one app for note taking, another for
scheduling, web browsers for asking AI questions, and no tool at all for condensing the
dozens of PDF slides distributed by instructors. This fragmentation causes:
\begin{itemize}[leftmargin=*]
  \item \textbf{Time loss} --- switching between tools and re-reading long PDFs that contain only a few exam-relevant points.
  \item \textbf{Lack of self-assessment} --- students rarely create their own practice questions, so weak topics are discovered only during exams.
  \item \textbf{Poor planning visibility} --- study sessions are not tracked, so students cannot measure consistency or progress.
  \item \textbf{No personalization} --- generic AI chat services do not keep study notes, plans, and progress under one authenticated, per-user account.
\end{itemize}
StudyMate AI addresses these problems by unifying AI assistance and study management in
one authenticated mobile application.

\section{Objectives of the Project}
\subsection{General Objective}
To design, implement, and evaluate an AI-powered, cross-platform mobile study companion
application within a fixed thirteen-week schedule using modern software engineering and
project management practices.

\subsection{Specific Objectives}
\begin{enumerate}[leftmargin=*]
  \item To implement secure user authentication (registration, login, password reset) using Firebase Authentication.
  \item To build a real-time AI chat module that streams Google Gemini responses token by token through a Node.js backend.
  \item To implement PDF summarization that converts uploaded lecture documents (up to 10\,MB) into structured study notes.
  \item To implement an automatic quiz generator producing multiple-choice questions with configurable count (5/10/15) and difficulty (easy/medium/hard).
  \item To implement per-user local persistence for notes and study sessions using AsyncStorage.
  \item To provide a personalized dashboard showing study progress and one-tap access to every module.
  \item To manage the project with a documented work breakdown structure, schedule (Gantt chart), critical-path analysis, effort estimate, and risk register.
  \item To verify the system through a documented test plan covering unit, integration, and system levels.
\end{enumerate}

\section{Scope of the Project}
The scope of the project includes:
\begin{itemize}[leftmargin=*]
  \item A mobile client (Android-first, iOS-capable) developed with Expo/React Native and TypeScript;
  \item A REST backend (Node.js, Express) exposing three AI endpoints --- chat, PDF summarization, and quiz generation --- with retry logic and input validation;
  \item Firebase email/password authentication with display-name profiles and password-reset e-mail;
  \item Local, device-side persistence of notes and study sessions, isolated per authenticated user;
  \item Complete project management artifacts: schedule, WBS, CPM network, effort and cost estimation, and risk management.
\end{itemize}
The following items are explicitly \textbf{out of scope} for this release: cloud
synchronization of notes across devices, social or collaborative study features,
payment/subscription services, and iOS App Store or Google Play store publication
(development builds and Expo Go are used for evaluation).

\section{Methodology Overview}
The project follows an \textbf{iterative, Agile-inspired life cycle} organized into five
two-week development sprints sandwiched between an inception/planning phase and a
closing testing-and-release phase. At the end of each sprint a potentially shippable
increment is demonstrated, requirements are re-prioritized, and the next sprint is
planned. Project management artifacts (schedule, risks, effort) are maintained as living
documents and reviewed weekly. Chapter~\ref{ch:pm} describes the methodology and all
management artifacts in detail.

\chapter{Project Management Plan}\label{ch:pm}

\section{Software Development Life Cycle Model}
For StudyMate AI we selected an \textbf{iterative, Agile-inspired life cycle}
(scrum-like sprints without the full Scrum ceremony overhead, which is impractical for
a two-member student team). The rationale is:

\begin{itemize}[leftmargin=*]
  \item \textbf{Evolving requirements.} AI-driven features (chat quality, summary format, quiz JSON contract) needed repeated tuning based on real model output; a strictly linear (waterfall) plan would have frozen these requirements too early.
  \item \textbf{Early and continuous risk reduction.} The riskiest integration --- the Gemini API --- was prototyped in the second sprint, so feasibility problems would have surfaced while schedule buffer still existed.
  \item \textbf{Frequent feedback.} A working increment was demonstrated at the end of every two-week sprint to the course faculty and fellow students, and feedback was folded into the next sprint.
  \item \textbf{Small team.} Two developers can coordinate with lightweight daily check-ups instead of heavy documentation gates, which Agile explicitly supports.
\end{itemize}

Figure~\ref{fig:sdlc} illustrates the selected model: after a short inception phase the
team iterates through requirement, design, implementation and testing activities in
two-week sprints, and a working increment is released at the end of the cycle.

\section{Feasibility Study}
\begin{itemize}[leftmargin=*]
  \item \textbf{Technical feasibility.} All required technologies (Expo, Firebase, Express, Gemini API) are mature, documented, and available in free tiers. A proof-of-concept call to Gemini was successfully executed in week 1, confirming feasibility. \textit{Verdict: feasible.}

\end{itemize}

(Figure~\ref{fig:architecture}). The mobile client never talks to the AI model

\section{Backend Implementation}\label{sec:impl-backend}
The backend (\texttt{backend/server.js}, 500 lines) is intentionally small: three
routes plus a shared retry helper.

\subsection{Retry Policy for the Gemini API}
All model calls are wrapped in an exponential-backoff retry loop that reacts to
transient HTTP statuses (429 and 5xx), which was essential during Sprint~2 rate-limit
incidents (risk R1).

\begin{lstlisting}[style=js,caption={Exponential-backoff retry helper (excerpt).},label={lst:retry}]
async function generateWithRetry(contents, maxRetries = 4) {
  let lastError;
  for (let attempt = 0; attempt <= maxRetries; attempt++) {
    try {
      return await ai.models.generateContent({
        model: GEMINI_MODEL,
        contents,
      });
    } catch (error) {
      lastError = error;
      const status = error?.status || error?.code;
      const shouldRetry =
        status === 429 || status === 500 || status === 502 ||
        status === 503 || status === 504;
      if (!shouldRetry || attempt === maxRetries) throw error;
      const delay = Math.pow(2, attempt) * 1000;  // 1s, 2s, 4s, 8s
      await new Promise((r) => setTimeout(r, delay));
    }
  }
  throw lastError;
}
\end{lstlisting}

\subsection{Streaming Chat Endpoint}
\texttt{POST /chat} sets plain-text streaming headers and pipes each Gemini chunk to
the client as soon as it arrives, which keeps perceived latency low even for long
answers (Listing~\ref{lst:stream}).

\begin{lstlisting}[style=js,caption={Streaming response of \texttt{POST /chat} (excerpt).},label={lst:stream}]
res.setHeader("Content-Type", "text/plain; charset=utf-8");
res.setHeader("Cache-Control", "no-cache, no-transform");
res.flushHeaders();

const stream = await ai.models.generateContentStream({
  model: GEMINI_MODEL,
  contents: message.trim(),
});
for await (const chunk of stream) {
  if (chunk.text) res.write(chunk.text);
}
res.end();
\end{lstlisting}

\subsection{PDF Summarization Endpoint}
\texttt{POST /summarize-pdf} receives the file through Multer (in-memory, limited to
10\,MB), base64-encodes it, and sends it to Gemini together with a prompt that
enforces a fixed six-section structure (Main Topic, Key Points, Definitions,
Concepts, Short Summary, Exam Notes). The response is returned as
\texttt{\{fileName, summary\}}.

\subsection{Quiz Generation with Schema Validation}
The quiz route prompts the model to return \emph{strict JSON} and then validates the
schema before anything reaches the client: exactly the requested number of questions,
exactly four options each, and an integer \texttt{correctAnswer} in $[0,3]$.
Listing~\ref{lst:quizval} shows the core of the validation; any violation produces a
controlled error instead of a broken quiz screen.

\begin{lstlisting}[style=js,caption={Server-side quiz schema validation (excerpt).},label={lst:quizval}]
const quiz = JSON.parse(text);           // 500 on parse error
if (quiz.questions.length !== questionCount)
  throw new Error(`Expected ${questionCount} questions`);

for (const question of quiz.questions) {
  if (!Array.isArray(question.options) || question.options.length !== 4)
    throw new Error("Invalid question format.");
  if (!Number.isInteger(question.correctAnswer) ||
      question.correctAnswer < 0 || question.correctAnswer > 3)
    throw new Error("Invalid question format.");
  if (!question.options.every((o) => typeof o === "string" && o.trim()))
    throw new Error("Invalid options format.");
}
res.json(quiz);
\end{lstlisting}

\section{Authentication Module}
\texttt{firebaseConfig.ts} initializes Firebase once and exports the \texttt{auth}
instance. The registration flow validates completeness, password match and minimum
length client-side, then calls \texttt{createUserWithEmailAndPassword} and
\texttt{updateProfile} so that the display name powers the personalized dashboard.
Login maps Firebase error codes to friendly messages
(Listing~\ref{lst:login}) and, on success, replaces the navigation stack with the
tabbed area. The \emph{Forgot password} link triggers
\texttt{sendPasswordResetEmail}.

\begin{lstlisting}[style=ts,caption={Login with Firebase error mapping (excerpt).},label={lst:login}]
try {
  await signInWithEmailAndPassword(auth, email.trim(), password);
  router.replace("/(tabs)");
} catch (error: any) {
  if (error.code === "auth/user-not-found")
    alert("No account found with this email.");
  else if (error.code === "auth/wrong-password")
    alert("Incorrect password.");
  else if (error.code === "auth/invalid-credential")
    alert("Invalid email or password.");
  else alert("Login failed. Please try again.");
}
\end{lstlisting}

\section{Feature Modules}
\subsection{Home Dashboard}
The dashboard subscribes to \texttt{onAuthStateChanged} for the user name and loads
the study sessions of the current user on every focus (\texttt{useFocusEffect}). It
derives \texttt{totalSessions}, \texttt{completedSessions}, and the percentage used by
the animated progress bar, and exposes the feature grid plus a sign-out action with
confirmation dialog.

\subsection{AI Chat}
The chat screen keeps the message history in component state, posts to
\texttt{/chat}, and consumes the response with a streaming \texttt{fetch} reader; each
received chunk is appended to the current AI bubble, producing the typewriter effect.
A typing indicator and an empty-state greeting cover the waiting period.

\subsection{PDF Summary}
\texttt{expo-document-picker} selects the file; the screen builds a
\texttt{FormData} upload and renders the returned summary. All failure modes (no file,
oversized file, backend down, Gemini unavailable) map to human-readable alerts.

\subsection{Quiz}
The quiz screen is a small state machine: \emph{setup $\rightarrow$ generating
$\rightarrow$ answering $\rightarrow$ result}. Answers are locked after selection,
colored feedback is shown, the explanation is displayed, and the final screen reports
score and percentage with a retry action.

\subsection{Notes}
Notes implements full CRUD against AsyncStorage under the key
\texttt{@studymate\_notes\_\allowbreak<uid>} (Listing~\ref{lst:noteskey}). A search box filters
title and content in real time; editing reuses the same editor card.

\begin{lstlisting}[style=ts,caption={Per-user storage key isolation.},label={lst:noteskey}]
const storageKey = `@studymate_notes_${currentUserId}`;
const savedNotes = await AsyncStorage.getItem(storageKey);
// writes mirror reads: setItem(storageKey, JSON.stringify(notes))
\end{lstlisting}

\subsection{Study Planner}
The planner stores sessions under \texttt{studymate\_study\_\allowbreak sessions\_\allowbreak<uid>} and
supports add, toggle-complete, and delete with confirmation. The dashboard re-reads
this key whenever it gains focus, so progress updates propagate automatically between
the two screens.

\section{Testing Strategy}
Testing followed the V-model mapping of the development phases:
\begin{itemize}[leftmargin=*]
  \item \textbf{Unit level} --- each backend route handler and each client function was exercised manually with valid and invalid inputs during development;
  \item \textbf{Integration level} --- client--backend pairs (chat, PDF, quiz) were tested against the real Gemini API on the emulator;
  \item \textbf{System level} --- the complete app was tested against the requirement list (Table~\ref{tab:fr}) during Sprint 5 and the dedicated testing phase (W12);
  \item \textbf{User acceptance} --- five fellow students performed free exploration with a short task script during W13.
\end{itemize}
All test cases were recorded in a shared spreadsheet and later transferred to
Table~\ref{tab:tests}. A defect is reopened unless its fix passes both the original
failing case and a regression pass over the authentication and dashboard flows.

\chapter{Results and Discussion}\label{ch:results}

\section{Achieved Results}
At the end of the project (September 30, 2026) every \emph{Must-have} requirement of
Table~\ref{tab:fr} was implemented and verified:

\begin{itemize}[leftmargin=*]
  \item \textbf{Authentication.} Registration, login, password reset, and persistent sessions work through Firebase; per-user data isolation was verified (TC-28).
  \item \textbf{AI Chat.} Streaming answers appear in under three seconds on the university network; the retry policy absorbed all observed Gemini rate limits without user-visible failures after Sprint 2.
  \item \textbf{PDF Summarization.} Tested with 24 lecture PDFs (0.3--9.6\,MB) from three courses; summaries consistently contained all six requested sections and were judged ``exam-useful'' by four of five UAT participants.
  \item \textbf{Quiz Generation.} Generated over 120 quizzes during testing; server-side validation rejected 2 malformed model outputs, which were transparently regenerated. Average generation time: 4.8\,s for 10 questions.
  \item \textbf{Notes \& Planner.} CRUD plus search work reliably; dashboard progress stays consistent with planner state (TC-24/TC-25).
  \item \textbf{Schedule adherence.} All milestones of Figure~\ref{fig:gantt} were met; the final release coincides with the planned date (September 30, 2026). Effort finished at 320 person-hours against a 320 person-hour plan (2.5\% estimation error including contingency usage of zero).
\end{itemize}

\section{Discussion}
The iterative life cycle proved appropriate: the quiz JSON contract was rewritten once
after Sprint 3 feedback (the model initially returned markdown-fenced answers), and
the streaming endpoint replaced an earlier non-streaming design after Sprint 2
demonstrations --- both changes would have been expensive under a waterfall plan.
The critical-path plan was tight by design; in practice, float activities (notes,
planner, backend core) absorbed roughly four days of delays caused by emulator
networking issues, confirming the value of scheduling parallel non-critical work.

The most effective management practices were the weekly risk review, server-side
schema validation as a risk response to R3, and the ``demo or it did not happen''
sprint rule.

\section{Limitations}
\begin{itemize}[leftmargin=*]
  \item Notes and plans live only on the device (AsyncStorage); uninstalling the app removes them (risk R6, accepted for this release).
  \item A single LLM provider (Gemini) is supported; provider failure equals feature downtime even with retries.
  \item The web build of the Expo client was not part of the test matrix; Android was the reference platform.
  \item The Gemini key, although kept server-side, is a plain environment secret; a production system would use a secret manager and per-user quotas.
\end{itemize}

\chapter{Conclusion and Future Work}\label{ch:conclusion}

\section{Conclusion}
The StudyMate AI project delivered, in thirteen weeks, an authenticated mobile study
companion unifying conversational help, PDF summarization, self-assessment quizzes,
note taking, and study planning. The final product provides Firebase-backed accounts,
a streaming Gemini chat assistant, six-section PDF summaries, configurable
multiple-choice quizzes with instant feedback, searchable per-user notes, and a
planner whose progress appears on a personalized dashboard.

Equally important, the project was \emph{managed}, not just coded: a documented WBS, a
Gantt schedule with six milestones, a critical-path analysis matching the 88-day
window exactly, an effort estimate accurate to 2.5\%, and a risk register whose top
risk (API rate limiting) was mitigated in code before it affected users. All 30
system test cases pass at release, and the product was delivered on the planned
date, September 30, 2026.

\section{Future Work}
\begin{itemize}[leftmargin=*]
  \item \textbf{Cloud synchronization} of notes and plans (Firestore) with offline support, closing accepted risk R6.
  \item \textbf{Spaced-repetition quiz mode} that re-schedules incorrectly answered questions automatically.
  \item \textbf{Voice input and audio summaries} for hands-free study sessions.
  \item \textbf{Multi-model resilience}: a fallback LLM provider behind the same backend contract.
  \item \textbf{Analytics dashboard} with weekly study-time trends and streaks.
  \item \textbf{Public release} on Google Play with a privacy policy and production secret management.
\end{itemize}

\chapter{Glossary}\label{app:glossary}
\begin{description}[leftmargin=4.2cm,style=nextline]
  \item[CPM] Critical Path Method --- network scheduling technique that identifies the longest chain of dependent activities.
  \item[Gantt chart] Bar-chart view of the project schedule over time.
  \item[LLM] Large Language Model --- AI model that generates natural-language text (here: Google Gemini).
  \item[MCQ] Multiple-choice question.
  \item[MoSCoW] Prioritization scheme: Must / Should / Could / Won't have.
  \item[SRS] Software Requirements Specification.
  \item[Streaming] Server sends response incrementally as it is produced.
  \item[UAT] User Acceptance Testing.
  \item[WBS] Work Breakdown Structure --- hierarchical decomposition of project work.
\end{description}
